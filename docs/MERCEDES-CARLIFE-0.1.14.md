分支 `mercedes-carlife`，基于0.1.13提交 `62f9579f752efaec5c5878c1ee7249e8661ab9f8`。本版是针对已发现缺口的修复候选，尚无实车验收；不承诺消除所有卡顿或保证奔驰麦克风识别成功。

## 本轮报告实际证明什么

用户报告：长按方向盘语音键能呼出CarWith，小爱图标同样可以触发，但随后感觉CarPlay卡死；切换原车界面后无法自动恢复。

报告导出于2026-11-16 20:13（Asia/Shanghai），**实际安装0.1.12-debug/1120000**，APK SHA256 `e777b5e2c21cd9ec4862bd74a5759f4ee53c0c66dd23e37c8032ded169d49e98`。不能用它判定0.1.13媒体桥已实车验证。报告包含历史进程，下面只分析19:24–19:27新测试，不混用18:18的0.1.11记录。

设备为Xiaomi24129PN74C、Android16/API36，用户HyperOS3；CarWith4.0.9-20260629 (104000009)、CarLife8.8.5 (274)。奔驰GLC2602024，接收端Mercedes-Benz/MB_D-M-5，报告firmwareRevision5.0.0、sourceVersion320.17.8（不是完整MBUX固件版本）。通知使用权未开启；这不解释原生CarLife语音SETUP被拒。mcarplay的RECORD_AUDIO未授予，但网络接收车机麦克风本身不使用Android本地麦克风权限，不能据此认定故障原因。

两轮麦克风均为 `setupAccepted=false type=100 audioType=speechRecognition format=0x40`，最终 `carlifeWritten=0`：没有车机PCM成功回传的证据。旧日志没有保留具体RTSP拒绝码，因此不能断言是格式、端口还是资源拒绝。检查源码另发现：SETUP返回失败后仍无条件TEARDOWN该未建立的type100流，可能扩大接收端异常，必须修正；不能把这个风险当作已证实的唯一卡死原因。

## 与CarPToCarL的取舍

对照CarPToCarL1.2.51，commit `3cbc8e85544bcffcc2aa45f1f3c5e1c70f9ca715`：

- 采用 `AirPlayResourceState.claimAndPublish` 的原则：生成拟申请归属，等待modesChanged确认，期间不锁住事件仲裁；如果新changeModes已经到达，放弃提交旧申请。
- 把连接邀请与requestUI区分：邀请只允许取回未借用、约束不高于500的主屏；借屏/倒车期间不因重复邀请抢回画面。显式requestUI继续检查unborrow/take约束。
- CarPToCarL通用 `CarPlayResourceStreams` 会TEARDOWN并重新SETUP/RECORD屏幕。这辆奔驰0.1.11历史测试曾在该流程后约129ms关视频/事件通道，本版保留已建立屏幕连接，不照搬重建流程。
- 对照其输入流探针补完整RTSP目标、独立data/control端口和250ms延迟候选。但参考仓库的麦克风代码只是数包探针，不能直接证明解密/CarLife注入或奔驰识别已成功。
- 不关闭ACK超时、不伪造语音成功、不用定时强占屏幕掩盖仲裁问题。网络虚拟iAP2鉴权/ACK问题仍需独立定位。

## 0.1.14改动

1. 已识别奔驰推流期间、主屏归车机时的新ctrl邀请进入主屏申请工作队列；不要求销毁整轮会话。requestUI也走同一申请入口。重复待执行请求合并，显式UI意图优先，连接代数隔离。
2. modesChanged主动发布串行化；屏幕归属只在RTSP200、无非零plist状态且没有新的资源事件时提交。失败不把本地误标成“手机已拿回”。
3. 成功取回后复用原视频连接和加密计数，重发配置并请求新IDR。车机仍借屏/高约束、连接已更替时保持原状态，不周期抢屏，也不重复RECORD。
4. 麦克风声明独立本机UDP数据/控制端口，使用完整RTSP URL和有界250ms延迟；记录RTSP状态码、plist状态及控制端口是否声明，不记录音频/载荷。
5. 只有SETUP被确认接受的输入流才允许对应TEARDOWN；被拒直接关闭本机输入、清除临时语音态，保留视频/媒体/控制。已接受但3秒无认证输入时停止该输入，避免一直处在空收音状态；总收音时限仍为30秒。
6. CarLife回到唤醒词监听请求时结束上一轮显式录音。本版仍不启动常驻监听，也不添加本地手机麦克风回退。
7. 保留0.1.13歌曲信息、封面和默认关闭的歌词标题兼容；本轮日志尚不能验收这些功能。

控制端口的声明不代表实现所有RTCP反馈扩展；拒绝原因、真实认证包、CarLife写入以及用户实际识别结果仍须分别验证。

## 实车验证

- 覆盖安装同证书0.1.14-debug，先保留原蓝牙配对。先不播放音乐、不唤语音，确认正常画面和触摸。
- 切到原车主页，再按车机当前可用入口返回CarPlay。检查 `SCREEN: 奔驰取回主屏 fromRequestUi=... acquired=true`，随后出现新关键帧写入。新邀请被借屏/高约束拦住时应看到对应日志，不能用定时抢屏解决。
- 驻车且确认周边安全时测试倒车借屏/归还；倒车画面优先，归还后画面恢复；反复3次，观察是否有新的屏幕SETUP/RECORD或断线。
- 分别长按方向盘键和触摸小爱图标。记录是否出现错误、仅画面停还是音频/触摸一起停。麦克风成功的证据顺序是 `setupAccepted=true` → `authenticated`增加 → `carlifeWritten`增加 → 小爱确实识别；任何前一项都不能替代后一项。
- 若仍SETUP被拒，记录 `rtspStatus`/`protocolStatus`；应有 `no TEARDOWN for uncreated stream`，视频与普通触摸仍可用。若已接受但无包，应出现 `no authenticated input before deadline`。
- 导出脱敏报告，注明上述每一步时间及返回CarPlay的具体操作。一次仅验证一个场景，最后再组合音乐、语音与倒车。

不要求删除配对；只有车机完全不再显示CarPlay入口时才另外排查公告/蓝牙。若车机不发归还、requestUI或新邀请，本版不会自行抢屏，需新的事件证据。本版也不宣称修复packet105、完成GPS/仪表导航或证明60FPS稳定显示。原始用户报告不入库。
