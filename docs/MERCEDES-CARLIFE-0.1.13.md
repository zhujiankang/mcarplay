# 0.1.13：正在播放、歌曲封面与歌词兼容候选

分支 `mercedes-carlife`，基于0.1.12提交 `83f0412e4b7e7dab00b2d0fe78b92a03d8e4820f`。本版补齐媒体信息通路，延续上一版奔驰屏幕接管与语音事件修复；尚无本版实车媒体显示验收。

## 为什么切歌正常，仪表仍没有封面

按键从车机进入手机，与歌曲信息从手机回到车机是独立通路。此前可以把上一首/下一首转成 CarLife 硬按键，但：

1. CarLife `0x10035` 媒体信息没有解析，歌名、歌手、专辑及图片没有送入媒体桥。
2. 网络 iAP2 对 `0x5000 StartNowPlayingUpdates` 的代码处理只是 `0x5001` 空状态；蓝牙 iAP2 保活阶段也未处理真实媒体订阅更新。
3. 封面需要独立文件传输，只有歌曲标题或一个图片编号不足以显示图片。

用户最近提供的0.1.11报告中，18:18:35–18:19:30多次记录未处理的 `0x10035`，字段1–4为文本、字段5从3611字节变为29769/19714字节，符合媒体信息和图片字段形状。它没有保留明文图片，因而不能仅凭长度确认这些字节的图像格式或具体内容。该轮还记录 `0x10036` 进度消息。

奔驰蓝牙协商会话表是 `1/k0/v2, 2/k1/v2, 3/k2/v1`：控制1、文件传输2、EA3。因此不能把文件传输固定发往本地默认编号12，也不能把入向编号2总当作EA触摸数据。

日志中的 `0x5000/0x5002/0x5003` 出现在车机能力列表中，**不是实际媒体订阅已经收到的证明**。该报告未确认实际媒体订阅或封面接收成功。本版会记录真实订阅、传输和接收结果；不据能力声明认定奔驰仪表必然显示封面。

## 本版实现

### 媒体数据来源

- 按 Baidu `CarlifeMediaInfo` protobuf 字段解析歌名、歌手、专辑、图片、时长、歌曲ID及来源。兼容小米日志呈现的直接消息，以及标准列表包装；拒绝超长、截断、重复字段和无效UTF-8，错误不从命令读取线程逃逸。
- CarLife媒体消息只有已认证且进入视频运行阶段的正式会话可以发布；系统媒体会话回退仅在正式源生命周期内轮询。源端结束、旧会话迟到回调、会话替换均清除或隔离旧数据。
- 已获通知使用权时，可使用系统MediaSession的标题、歌手、专辑、封面、播放状态及进度。CarLife 与系统媒体会话合并图片/歌词前核对歌曲，避免把旧播放器的封面配给新歌曲。
- CarLife自身提供的图片不依赖通知使用权。系统媒体会话读不到信息时，仍可使用CarLife原生媒体信息；通知授权不保证所有播放器都公开完整字段。
- 图片解码/缩放/JPEG编码在独立工作线程，最大512像素、输出上限128KiB；无HTTP取图、无额外歌词服务、无图片落盘。相同图片复用缓存，失败结果也缓存，避免每次轮询重复解码。
- 无系统媒体会话时，播放状态根据源媒体通道活动提供有限回退；不能据此证明实际扬声器出声。CarLife进度消息本版未直接映射，避免在单位未核实前编造播放位置；准确位置以可读的系统媒体会话为准。

### 车机媒体协议与封面

- 蓝牙iAP2和网络/隧道iAP2均接入独立订阅状态，收到实际 `0x5000` 后发送 `0x5001`，数据晚到时周期补推；`0x5002` 停止订阅，`0x5003` 记录图片属性请求。没有订阅时不主动冒充车机已同意接收。
- 使用正确TLV：媒体组标题1、时长4、专辑6、歌手12、图片传输ID26；播放组状态0、进度1、应用名7。图片ID为单字节，图片本体不塞进这个字段。专辑名与图片ID字段不会混用。
- 按协商会话种类选择控制、文件和EA编号。遵守对端包长，限制可选媒体的积压与未确认窗口。入向文件响应有界排队、去重并更新确认水位，避免和EA混淆。
- 封面先发 `SETUP(id,u64大小,type=2)`，等待车机 `START` 后才发首/中/末分块，等待 `SUCCESS`。按真实图片内容变化换编号，歌词行不反复重传封面；连接内不复用已用完的图片ID。
- 切歌取消未完成图片，忽略迟到的旧ID响应。图片拒绝、暂停或超时会关闭本连接的图片尝试，继续文字更新；链路ACK停顿会暂停新媒体并丢弃尚未发送的可选队列；已发送的包不能跳过序号，仍保留原有重试与终止策略，永久不确认仍可能使链路失败。
- 当前图片候选为有界JPEG；并未完成所有车机图片格式/尺寸偏好的适配。收到 `artworkAttributesReceived` 不等于已满足对端的全部图片格式要求。

### 歌词的边界

当前实现的标准NowPlaying字段没有专用逐行歌词窗口。本版增加默认关闭的 **“仪表歌词兼容模式（实验）”**，位置在设置→显示：

- 仅使用CarWith实际提供、能与歌曲基线关联的歌词行，不联网找歌词，也不从视频OCR猜歌词。
- 兼容行暂时替换歌曲标题，真实歌手、专辑和封面仍取当前歌曲；不宣称是奔驰原生歌词功能。
- 校验来源、歌曲ID（可用时）及艺术家/专辑关系，并在有系统媒体会话时再次校验当前歌曲。超过5秒失效、切歌或来源不匹配时退出歌词行，防止上一首歌词残留。
- 车机可能截断、缓存或不刷新标题，因此不能保证完整歌词、逐字高亮、滚动方式或显示区域。播放器没有提供可识别歌词时，开关不会生成歌词。

## 新日志与验证顺序

1. 覆盖安装同证书0.1.13-debug，先保持已有配对，确认原来的画面、音频、切歌与倒车切换没有回归。
2. 先关闭歌词兼容模式，播放一首有明确封面的歌曲，再打开奔驰仪表的媒体/正在播放页面；记录仪表和中控原车媒体页分别是否显示标题、歌手、专辑及封面。先验证正常歌名/封面，再验证歌词。
3. 查看这些阶段，不能用前一个阶段代替后一个：

| 日志 | 证明什么 |
| --- | --- |
| `carlifeInfoReceived=... artworkBytes=...` | CarLife媒体信息已解析，原始图片字段存在多少字节。 |
| `artworkNormalized=true bytes=...` | 手机侧已得到有界JPEG候选。 |
| `subscribed fileTransfer=...` | 这条iAP2连接实际收到媒体订阅，及是否协商文件通道。 |
| `updatesQueued=... artworkDeclared=...` | 已排入媒体更新，不等于仪表实际显示。 |
| `artworkSetup id=... bytes=...` | 已提出图片传输请求。 |
| `artworkSuccess id=...` | 车机文件协议报告成功；仍需用户确认可见封面。 |

4. 若有CarLife解析记录但没有 `subscribed`，先确认仪表/原车媒体页面当前选择了CarPlay源，并记录车机是否有媒体订阅。不能把“车机能力列表含0x5000”当作实际订阅。
5. 连续切歌3–5次，确认新歌与封面匹配、暂停/恢复状态合理；图片不支持时应保留文字和主视频连接。可比较iPhone在同车同页面的显示，以确认车机本身提供哪些区域。
6. 再按需开启歌词兼容，测试实际提供歌词的播放器。观察是正常歌名、歌词行，还是车机不刷新；切歌后不应出现上一首歌词/封面。
7. 最后复测方向盘按键和驻车安全条件下的倒车接管/归还，导出诊断并注明音乐App、页面位置、故障时间和通知使用权状态。

新诊断只记录状态/计数/字节数，不写歌名、歌手、歌词正文、图片、内容哈希或URI；启用媒体传输后关闭相应蓝牙原始字节转储，网络媒体CSM也隐藏载荷。不会自动上传媒体内容或诊断。

## 依据与限制

字段定义核对 [Baidu CarlifeMediaInfo protobuf](https://github.com/milesking/apollo-DuerOS/blob/6a07419818f46aadda34c5f55e63d4a1fc8136ef/CarLife-Vehicle-Lib/LibSource/protobuf/proto/CarlifeMediaInfoProto.proto)。iAP2字段、图片传输及歌词兼容策略对照CarPToCarL 1.2.51，commit `3cbc8e85544bcffcc2aa45f1f3c5e1c70f9ca715`；原MIT通知保留，未打包SDK或第三方APK。

本地测试包括加密CarLife媒体回放、实际链路订阅/封面START/分块/SUCCESS往返、奔驰文件编号2与EA3分流、重放、无确认回退、限包/限队列、歌词匹配与失效以及隐私。Android图片解码实际效果、奔驰仪表显示及歌词刷新需要实机验证。原有网络iAP2 packet105未确认等问题仍需独立定位；本版不宣称消除了所有ACK异常、完成GPS/仪表导航或支持奔驰原生歌词窗口。
